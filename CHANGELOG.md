## v1.0.0dev - [date]

Initial release of nf-core/hlarnaseq, created with the [nf-core](https://nf-co.re/) template.

### `Added`

- Added required `--rna_samples` and `--hla_region` inputs and extraction of arcasHLA-ready paired MHC FASTQs with samtools.
- Added per-sample validatefastq pairing validation for extracted arcasHLA reads, with validation logs under `arcashla/validation/`.
- Added an `ARCASHLA_GENOTYPE` step that runs `arcasHLA genotype` on validated RNA reads (configurable via `--arcashla_genes`), writing per-sample results under `arcashla/genotype/`. Genotyping runs inside a dedicated, operator-prepared `arcas-hla` Conda environment.
- Added an `ARCASHLA_COMBINE` step that merges per-sample arcasHLA genotype JSON results into a single long-format `arcashla/arcasHLA_combined.csv`, using a new `bin/combine_arcashla_genotypes.R` script.
- Added a standalone `bin/call_hla_consensus.py` script (argparse CLI) that calls a consensus HLA allele per WGS individual by combining `ARCASHLA_COMBINE` RNA genotypes with `HLALA_COMBINE` WGS genotypes via an RNA/WGS sample key. Not yet wired into the Nextflow workflow.
- Added a `--sample_key` pipeline parameter (comma-separated `rnaseq_sample_id,wgs_sample_id` mapping) and a new `HLA_CONSENSUS` process that wires `bin/call_hla_consensus.py` into the Nextflow workflow, running automatically when `--rna_samples`, `--wgs_samples`, and `--sample_key` are all provided, with results written to `hla_consensus/`.
- Added optional `--rna_excluded_samples`/`--wgs_excluded_samples` parameters (plain-text sample ID lists) and `--hla_consensus_truncate_fields` (default `2`), passed through to `HLA_CONSENSUS`.
- Added a `bin/consensus_to_hlapm.py` script that converts `hla_consensus.rna_wgs_hla_consensus.tsv` into one per-individual, 2-column HLApm input TSV per WGS group, filtered by a new `--hlapm_allowed_loci` allow-list (default `A,B,C,DRB1,DQA1,DQB1,DPA1,DPB1,DOA,DOB,G,E,F`), and a `bin/hlapm_build_personalized_ref.R` script (ported from `artifacts/scripts/hlapm-personref.R`) that runs [HLApm](https://github.com/davenportlab/HLApm)'s `bulkRNA_build_personalized_HLA_ref()` on those per-individual TSVs.
- Added `HLAPM_PREPARE_INPUT` and `HLAPM_BUILD_REF` processes and a new `HLAPM` subworkflow that wire the above scripts into the Nextflow workflow, running automatically whenever `HLA_CONSENSUS` runs (i.e. whenever `--rna_samples`, `--wgs_samples`, and `--sample_key` are all provided). `HLAPM_BUILD_REF` invokes HLApm inside a dedicated, operator-prepared `hlapm` Conda environment via `conda run -n hlapm`. Results are written to `hlapm/input/<WGS_sample_ID>.tsv` and `hlapm/personalized_ref/out/<individual_ID>/<allele>.{fa,gtf}`.
- Added a new, now-mandatory (once `--rna_samples`, `--wgs_samples`, and `--sample_key` are all provided) `--hlapm_repo` pipeline parameter pointing to a local, pre-cloned HLApm checkout, enforced via a new `hlapmRepoExistsError()` hard-error check mirroring the existing `hlalaGraphDirExistsError()` precedent.
- Vendored the [nf-core/modules `STAR_GENOMEGENERATE`](https://github.com/nf-core/modules/tree/master/modules/nf-core/star/genomegenerate) module (pinned to STAR 2.7.11b, matching the version used by nf-core/rnaseq to build this pipeline's test data) and added a new `HLAPM_LIST_STAR_TARGETS` local module and `HLAPM_STAR_INDEX` subworkflow, wired in immediately after `HLAPM`. It discovers every allele FASTA/GTF pair actually present under `hlapm/personalized_ref/out/<individual_ID>/*.fa` (not from any input/consensus TSV), deduplicates them by a content hash (sha256 of FASTA+GTF, not by allele name, since HLApm does not explicitly guarantee identical output for the same named allele call across individuals), and builds one shared STAR genome index per distinct allele under `hlapm/star_index/<allele_key>/star/`. `hlapm/star_index_targets/unique_alleles.csv` and `sample_alleles.csv` record the dedup mapping. Unlike the rest of the pipeline, this step expects STAR from a container (`-profile singularity`/`docker`) or an auto-managed Conda environment, not an operator-prepared one.
- Vendored the [nf-core/modules `STAR_ALIGN`](https://github.com/nf-core/modules/tree/master/modules/nf-core/star/align) module (pinned to the same STAR 2.7.11b version used for indexing) and added a new `HLAPM_RESOLVE_SAMPLE_ALLELES` local module plus `HLAPM_STAR_ALIGN` subworkflow, wired in immediately after `HLAPM_STAR_INDEX`. For every RNA sample with one or more personalized HLA allele references, this aligns that sample's arcasHLA MHC-extracted reads against every one of its allele-specific STAR indexes (one `STAR_ALIGN` job per `(RNA sample, allele)` pair, reusing the same reads across each of that sample's alleles). `HLAPM_RESOLVE_SAMPLE_ALLELES` bridges `sample_alleles.csv`'s WGS-individual-ID/`RNA_ONLY:<rna_id>` keying back to real RNA sample ids using `--sample_key` (broadcasting a WGS individual's full allele set to every RNA sample matched to it), publishing the resolved mapping as `hlapm/star_align/rna_sample_alleles.csv`. Alignment output (`STAR --outSAMtype BAM SortedByCoordinate`) is written under `hlapm/star_align/<rna_id>/<allele_key>/`. Continues the same STAR container/Conda exception as `STAR_GENOMEGENERATE`.
- Vendored the [nf-core/modules `SAMTOOLS_SORT`](https://github.com/nf-core/modules/tree/master/modules/nf-core/samtools/sort) module and added two new local modules (`HLAPM_COMBINE_GTF`, `HLAPM_QUANTIFY_READS`) plus a new `HLAPM_STAR_QUANTIFY` subworkflow, wired in immediately after `HLAPM_STAR_ALIGN`. For every `(RNA sample, allele)` pair, `SAMTOOLS_SORT` additionally queryname-sorts `STAR_ALIGN`'s coordinate-sorted BAM (`samtools sort -n`, published as `hlapm/star_align/<rna_id>/<allele_key>/<rna_id>.<allele_key>.queryname.bam`, alongside the unaffected coordinate-sorted BAM). `HLAPM_COMBINE_GTF` concatenates every distinct allele's GTF into one cohort-wide `hlapm/quantify/combined.gtf` (comment lines stripped), built once per pipeline run. `HLAPM_QUANTIFY_READS` then runs the legacy, unmodified Python 2.7 `make_a_table_210804_allHLAgenes.py` script (added to `bin/`) once per RNA sample, over that sample's full set of queryname-sorted per-allele BAMs plus `combined.gtf`, producing `hlapm/quantify/<rna_id>/<rna_id>.edit_distance.tsv` (per-read edit-distance/gene-assignment table) and `.stat.txt` (run statistics), run inside a new, dedicated, operator-prepared `hlapm-quantify` Conda environment (Python 2 + `pybam` + `intervaltree`; R packages for gene-level summarization are deliberately not added yet). **This is a partial quantification step**: it stops at the per-read edit-distance table and does not yet produce a gene-level read-count summary (`<rna_id>.HLA_gene_summary.tsv`) - that requires an additional R summarization step, deferred to a later iteration.
- Added a new `bin/summarize_hla_readcounts.R` script (adapted from `davenportlab/HLApm_farm_pipeline`'s `04_04_24_summarize_readcounts_script.R`) and a new `HLAPM_SUMMARIZE_READCOUNTS` local module, wired into `HLAPM_STAR_QUANTIFY` immediately after `HLAPM_QUANTIFY_READS`. For every RNA sample, it turns that sample's `<rna_id>.edit_distance.tsv` per-read table into a per-gene read count, keeping only non-`ambiguous` reads with a winning-gene edit distance at or below a new `--hlapm_quantify_max_edit_distance` parameter (default `16`), and writing `hlapm/quantify/<rna_id>/<rna_id>.HLA_gene_summary.tsv` (columns `gene_name`, `n_reads_mapping`). This closes the "stops at the per-read table" gap left open by the previous bullet. Runs inside the same `hlapm-quantify` Conda environment, which now also needs R (>= 4.0) plus the `dplyr`/`tidyr` CRAN packages.

### `Changed`

- Changed `HLALA_COMBINE` to emit tab-separated `hlala/HLA-LA_combined.tsv` (was comma-separated `HLA-LA_combined.csv`), adding a `Locus` column alongside `sample_id` and `HLA_allele`.
- Changed `bin/call_hla_consensus.py`'s `load_rna_wgs_key()` to read the new 2-column `--sample-key` CSV format (`rnaseq_sample_id,wgs_sample_id`), replacing the previous `--key-tsv` format (`sanger_sample_id_rnaseq`, `sanger_sample_id_wgs`, `USUBJID` columns, with `NoWgsSangerID:<USUBJID>` synthesis for present-but-empty WGS IDs). An RNA sample absent from the key is now always treated as `RNA_ONLY:<RNA_sample_ID>`.
- Changed the `HLA_CONSENSUS`→`HLAPM`→`HLAPM_STAR_INDEX`→`HLAPM_STAR_ALIGN` chain in `workflows/hlarnaseq.nf` from running only when `--rna_samples`, `--wgs_samples`, and `--sample_key` were all provided, to running whenever `--rna_samples` (and therefore `--sample_key`) are provided, independent of `--wgs_samples`. `HLALA` remains the only optional step, still gated solely on `--wgs_samples`.
- Changed `--sample_key` from an optional parameter to a required top-level input (added to `nextflow_schema.json`'s `input_output_options.required`). RNA samples absent from the key (or every RNA sample, when the key has zero data rows) continue to run through the existing `RNA_ONLY:<rna_id>` consensus fallback path.
- Changed `--hlapm_repo` from conditionally mandatory (required only when `--wgs_samples` was also provided) to unconditionally mandatory whenever `--rna_samples` is provided, via `hlapmRepoExistsError()` in `subworkflows/local/utils_nfcore_hlarnaseq_pipeline/main.nf` (still enforced solely by this custom check, not added to schema-level `required`, consistent with the existing `hlala_graph_dir` precedent).
- Added `assets/NO_WGS_HLALA_COMBINED.tsv`, a header-only (`sample_id`, `Locus`, `HLA_allele`) placeholder used as `ch_hlala_combined` whenever `--wgs_samples` is not provided, so `HLA_CONSENSUS`'s required `hlala_combined_tsv` input always receives a valid, parseable file. This is a channel-contract change: the `hlala_combined` workflow output is no longer ever empty once the mandatory chain runs (previously it was `channel.empty()` when `--wgs_samples` was absent); no current internal consumer distinguished "ran with WGS" from "ran without" by channel emptiness.
- Changed `-profile test` to exercise the full mandatory chain (`ARCASHLA`→`HLA_CONSENSUS`→`HLAPM`→`HLAPM_STAR_INDEX`→`HLAPM_STAR_ALIGN`) end-to-end under `-stub-run`, using a new header-only `tests/fixtures/sample_key_empty.csv` fixture (`--sample_key`) and a new placeholder `tests/fixtures/hlapm_repo_stub/` directory (`--hlapm_repo`, containing no real HLApm code or reference data). Added a `stub:` block to `HLAPM_BUILD_REF` that derives individual IDs from its `sample_tsvs` input and writes placeholder `out/<individual_ID>/<allele>.{fa,gtf}` files plus `versions.yml`, so `-stub-run` never shells out to `conda run -n hlapm`. Fixed `ARCASHLA_COMBINE`'s existing `stub:` block, which previously `touch`ed a 0-byte `arcasHLA_combined.csv`, to instead write a real header row plus one synthetic allele row per sample, so the now-unstubbed `HLA_CONSENSUS` can parse it.

### `Fixed`

- Fixed `bin/combine_arcashla_genotypes.R` returning an under-shaped, sample-ID-less row for samples whose arcasHLA genotype JSON is the valid-but-empty `{}` (not enough reads to genotype), so the combined CSV now correctly NA-pads alleles while preserving `rna_sample_id` for that sample.
- Fixed `bin/hlapm_build_personalized_ref.R` failing with `object 'DIR_personalizedHLA' not found`: HLApm's own `scripts/load_ref.R` requires this global variable to be set by its caller (per HLApm's own docs) before being sourced, but the script never set it.
- Fixed `HLAPM_LIST_STAR_TARGETS` finding zero alleles (both `hlapm/star_index_targets/*.csv` manifests ending up empty) whenever run against a real `HLAPM_BUILD_REF` output: HLApm's `bulkRNA_build_personalized_HLA_ref()` nests every individual's allele files one level deeper than the output directory it is given (under an extra `out/` it creates itself), so the previous fixed-depth directory scan never found the real per-individual directories. Discovery now recursively scans for `*.fa` files at any depth instead of assuming a fixed nesting level.
- Fixed `STAR_GENOMEGENERATE` requesting the `process_high` label's defaults (12 CPUs, 72 GB) regardless of genome size, which exceeded the CPUs/memory available on smaller machines. HLA allele references are a few KB each, so `conf/modules.config` now caps it at 1 CPU and 2 GB (`* task.attempt` on retry) for this process specifically.
